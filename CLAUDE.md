# Community Marketplace

## What This Is
A Next.js 16 (App Router) community marketplace that lets users browse local members, makers, and events. All auth is Clerk — shoppers use optional modal sign-in; vendors use a dedicated protected portal at `/vendor/*`.

## ⚠️ SHIPPING RULES — the iOS app is LIVE ON THE APP STORE (2026-08-02)
**Read this before every deploy.** The shipped app is a thin native shell that loads the **live hosted site** (`whatslocal-ios/capacitor.config.ts` → `server.url: 'https://whatslocal.ai'`; nothing web-side is bundled into the IPA). So **a CapRover deploy IS an app update** — it reaches every App Store user on their next launch, with no review, no submission, no way to roll back through Apple. That's the superpower and the danger.

**Ships instantly via CapRover (no submission):** every page/component/style in `app/` + `components/`, all API routes, DB migrations, connector/Supabase logic, AI prompts, push/email sending, copy, pricing-page content, tier gating, bug fixes.

**Requires a new Xcode build + App Review** (anything compiled into the IPA): **splash screen** (`ios/App/App/Assets.xcassets` + `Splash.storyboard`) and **app icon**; app name / version / build number; **`capacitor.config.ts` itself** — it's compiled to `capacitor.config.json` inside the bundle, so `allowNavigation`, `presentationOptions`, `contentInset`, `backgroundColor`, and even changing `server.url` all need a rebuild; Capacitor plugins (NFC, camera barcode, Google auth, push, StoreKit IAP); `Info.plist` permission strings; `App.entitlements`; the offline fallback page in `www/`.

**THE RULES — a web deploy is still bound by App Store guidelines. Breaking one of these gets the app PULLED, not merely rejected, because it never passed review:**
1. **NEVER un-hide the Stripe subscription paywall in the native app.** Apple 3.1.1 forbids selling digital subscriptions outside IAP. `BillingPlans` / `UpgradePrompt` / the `/join` done-screen / the VendorHome upsell all hide via `useIsNativeApp()` (`lib/native.ts`). Treat that gate as **build-gated, not web-gated** — never "simplify" it away, never render a Stripe checkout path when `isNativeApp()`.
2. **NEVER enable the ad pixels without wiring ATT first.** Setting `NEXT_PUBLIC_META_PIXEL_ID` / `NEXT_PUBLIC_GOOGLE_ADS_ID` / `NEXT_PUBLIC_GA4_ID` makes the *native app* "track" per Apple's definition. That requires (a) an ATT prompt gating them (`@capacitor-community/app-tracking-transparency` — a native change) and (b) a Tracking declaration in App Store Connect. The 2026-07-29 App Review reply truthfully said no tracking occurs; flipping these on a web deploy makes that statement false. See Pending/TODO.
3. **Don't ship a web change that would raise the app's age rating or add a reviewable capability** (new UGC surface without report/block, gambling, etc.). Moderation exists (see [[ugc-moderation]]) — keep any new user-content surface inside it.

**THE BUILD TRAP now protects the App Store app, not just the website.** `NEXT_PUBLIC_*` is inlined at build time and `next build` loads `.env.local` (demo `=1` locally). `.env.production.local` pins `NEXT_PUBLIC_DEMO_MODE=0` and `pk_live` — **never remove those lines.** The pre-deploy gate is mandatory, every time: `PORT=3100 npx next start` → `curl -sI localhost:3100/vendor` **must be 307 → /vendor/sign-in**. A **200 means demo mode is baked ON** and that build must not ship — it would open the whole vendor portal (products, orders, customer DMs) to every App Store user, unauthenticated. Grepping the bundle does NOT work (minification folds the constant away). Full detail in **Demo Mode** below.

**APNs environment (verified 2026-08-02, currently CORRECT — don't "fix" it):** CapRover prod has `APNS_ENV=production`, which matches App Store builds — Xcode rewrites `aps-environment` to `production` on distribution export regardless of the `development` value in `App.entitlements`. So push to real App Store users works. The mismatch now runs the *other* way: a **local Xcode debug build** on your own phone gets a **sandbox** token, registers it into the prod DB, and prod rejects + prunes it. Don't misdiagnose that as "push is broken" — and don't flip prod to `sandbox` to chase it.

**No forced-update mechanism exists.** Native changes only reach users who update from the App Store, so an old shell can be talking to a new web app indefinitely — keep web changes backward-compatible with the shipped native bridge (`lib/native-*.ts`).

## Error Tracking (Sentry) — errors only; PostHog keeps analytics + replay

**The split: Sentry owns errors end to end, PostHog owns product + session replay.** `capture_exceptions`
is now **`false`** in `lib/posthog-provider.tsx` — with both on, one crash filed two unrelated issues in two
dashboards, and PostHog only ever saw the browser half anyway.

- **Server (the reason this exists):** `instrumentation.ts` → `register()` loads `sentry.server.config.ts`
  (node) or `sentry.edge.config.ts` (edge — **required separately**, `middleware.ts`/clerkMiddleware runs
  there and the Node SDK cannot load in it). `export const onRequestError = Sentry.captureRequestError`
  is the hook that catches throws in route handlers, server components and server actions. **Verified**
  2026-08-10 against a local sink: a real throw in a route produced an `event` envelope.
- **Client:** `instrumentation-client.ts` (Next 16 convention — runs before the app is interactive, so it
  catches a crash during first paint that a React provider would miss) + `onRouterTransitionStart`.
  **Verified** the same way.
- **The PostHog link:** `beforeSend` attaches `contexts.posthog.session_replay` — the replay URL with a
  timestamp offset — so a Sentry issue opens the recording of the person who hit it. It **must import
  `posthog` as a module**, not read `window.posthog`: the app imports posthog-js, the global is not set,
  and reading it silently attached nothing (caught only because it was tested against a sink).
- **NO Sentry Session Replay, deliberately.** PostHog already records, and its recorder is the one carrying
  our `data-private` masking. A second rrweb would double script weight inside the iOS WKWebView *and*
  capture the conversation text we deliberately mask.
- **Trigger.dev worker is a SEPARATE deploy target** (`trigger/sentry.ts`, `@sentry/node`, registered via
  `tasks.onFailure` — `config.onFailure` is deprecated). Instrumenting Next.js does nothing for it, and it
  has the worst track record in the repo (the nightly sweep failed for weeks in silence). It fires only
  after retries are exhausted, and `flush(2000)`s because the runtime exits the moment a run settles.
  **`SENTRY_DSN` must be set on the Trigger.dev PROD environment** — a `tr_dev_` key in `.env.local` means

## Key Conventions
- **Applying a migration: `supabase db push` HANGS — use the Management API.** `supabase/.temp/pooler-url` has **no password in it**, so the CLI waits forever on an interactive prompt that never arrives without a TTY (this looks exactly like a network hang). Direct Postgres on **5432 is unreachable** from this machine; 6543 connects but still wants the password; there is no `psql`/`pg`/`psycopg2` installed. The working route needs no DB password at all — the CLI's Management API token sits in the macOS Keychain:
  ```bash
  TOKEN=$(security find-generic-password -s "Supabase CLI" -w | sed 's/^go-keyring-base64://' | base64 -d)
  curl -s -X POST "https://api.supabase.com/v1/projects/xbbnvkvlrucrzobhopgh/database/query" \
    -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"query":"select 1"}'
  ```
  (Keychain service `Supabase CLI`, account `supabase`; the value is `go-keyring-base64:` + base64 of `sbp_…`, so it must be decoded.) **Afterwards, register the migration** or the CLI's history diverges — this repo has already been bitten by out-of-sync history: `insert into supabase_migrations.schema_migrations (version, name, statements) values ('<version>','<name>', array[$stmt$-- applied via Management API$stmt$]) on conflict (version) do nothing;`
- **Dates in the feed are CITY-LOCAL — `lib/sf-date.ts`, never `toISOString().slice(0,10)`.** Every event is San Francisco time. UTC "today" becomes tomorrow at 5pm Pacific, which silently dropped that evening's events from the feed every single evening — at exactly the hour people look for something to do that night. Use `sfToday()`/`sfTomorrow()`; `startMinutes`/`endMinutes`/`isOnNow`/`hasEnded` read the free-text `event_time`. The timezone is fixed to the **city, not the viewer**: someone in London asking what's on tonight means tonight in SF.
- **Adding an event source means adding its poster hostname to `lib/image-hosts.ts` — ONE list, two consumers.** `next.config.ts` builds `images.remotePatterns` from it and `lib/image-utils.ts` builds its display allowlist from it. They used to be separate lists and **they disagreed**: next.config had every scraped host, `image-utils` trusted three (our storage + Unsplash), so `usableImages()` dropped every harvested poster, `ImageCarousel` returned `null`, and the whole event feed rendered as text — with the images sitting in the DB and in the API payload the entire time. Getting this half-right is silent in *both* directions: an unlisted host makes `next/image` throw in dev and **400 in production** (how a feed once shipped with 100 broken images), and an untrusted one shows a gradient with no error at all. `EVENT_POSTER_HOSTS` = shown; `TOLERATED_IMAGE_HOSTS` (`legacybusiness.org` hotlinks, Google Places) = optimisable but deliberately NOT shown — don't "fix" that by promoting them. Enumerable because the source list is hand-curated (`lib/sources/registry.ts`), not the open web.
- **`next/image` quality needs `images.qualities` in Next 16.** A `quality` prop whose value isn't on that allowlist is **silently ignored** and served at the default — no warning in a production build. That is how the profile hero's `quality={90}` had been coming out at 75 ever since the upgrade. Current list: `[75, 88, 90]` (88 = event posters, 90 = wide hero). Adding a new quality anywhere means adding it there, or the prop is decorative.
- **Prefer the source's ORIGINAL image, and verify before swapping.** Two sources hand us derivatives: SFPL renders Drupal style variants (widest 620px; strip `styles/<name>/public/` **and the `itok` query**, which signs the derivative only — keep it and the original path 404s), and WordPress sites put `<name>-WIDTHxHEIGHT.<ext>` in their JSON-LD (funcheap's was **80×80**). `fullSizeWordPressImage()` HEAD-checks before substituting, because that suffix pattern also matches ordinary filenames and a guessed URL that 404s renders *nothing* — strictly worse than a small image. Both run at ingest, deduped, never on a read path.
- **The model runs ONCE per new item, never per request.** Scraping is $0 (recipes, no LLM). Each event is audience-labelled once at ingest (~$0.11 for 800, ~$0.03/wk after). The only per-request call is reading one person's sentence. Never move labelling, embedding or extraction onto the read path.
- **Notifying a user = push + email, ALWAYS, via `lib/notify.ts`.** In this app "notify the user about X" is a **two-channel** action: (1) **native APNs push** (`lib/push.ts`) = the in-the-moment nudge, and (2) **email via Resend** (`lib/email.ts`) = the durable record that lands even when the phone's off / app not installed / permission denied. So whenever the task says *"notify the user about invites / a new message / an order update / …"*, wire it through **one** call, never `sendPushToUser`/`sendEmail` directly:
  - `notifyUser(clerkUserId, { title, body, url? })` — for a person (looks up their Clerk email).
  - `notifyMemberUser(memberId, { title, body, url? })` — for a business/organizer (bridges `member_id` → devices + `vendor_profiles.email`).
  - `notifyUserSafe` / `notifyMemberUserSafe` — fire-and-forget for request handlers: `void notifyMemberUserSafe(id, {...})`. **Use these on the hot path** — never await notifications on the response.
  - `title` = push title + email subject; `body` = push body + email body; `url` = deep link (opened on push tap **and** the email CTA; relative like `/vendor/network` is auto-absolutized). Both channels **no-op safely** when unconfigured or when there's no device/address — always safe to call. Resend is **verified working** (`whatslocal.ai` domain verified, tested live 2026-07-22); `APNS_*` push verified on-device same day. Call sites get wired in per feature; the primitive is done.
- Data comes from Community Connector Agent API (`NEXT_PUBLIC_API_BASE` / `CONNECTOR_URL`)
- **Client data fetching = SWR** (`lib/swr.tsx` `SWRProvider` in `app/layout.tsx`; `revalidateOnFocus` off, `dedupingInterval` 30s, `keepPreviousData`). **Use the shared hooks in `lib/data-hooks.ts`** (`useBroadcasts`/`useEventsFeed`/`usePosts`/`useDirectory`/`useFeatured`/`useBroadcast`/`useMemories`) — **never write a raw `useEffect`+`fetch` on mount** for these datasets. Same key = deduped across all consumers + cache survives tab-switch unmount (instant re-paint, background revalidate). **Never call `listMembers` from a client component** — route through `app/api/directory` (server-side, so `lib/api.ts`'s `revalidate:300` applies + connector stays off the browser). `next.config.ts` `experimental.staleTimes {dynamic:30,static:300}` extends the RSC router cache. See [[client-data-cache-swr]] memory.
- **One search box per screen — the top slot swaps with the tab.** On Home, `tab === 'events'` renders `components/feed/EventSearchBar.tsx` (the "What are you in the mood for?" box) *instead of* `HomeSearch`; other tabs get the business search back. **Never stack them** — two inputs on one screen compete for the same intent. The search state lives in `HomeTabs` and is passed to `PersonalizedEvents` as a `query` prop, because submitting also switches the view to For you; the component owns the input's *appearance*, never the search state. `text` is what's typed, `query` is what was submitted — **typing must never re-key the feed**, since each miss costs a model call.
- **Home tabs = `Events · Feed · Shop`; For you / What's on is a TOGGLE inside Events, not a tab.** Same events read two ways, so it sits next to the "Events near you" heading it modifies. `?tab=foryou` / `?tab=whatson` survive as legacy aliases (`lib/home-tab.ts LEGACY`) from when they briefly were tabs.
- **The device's position is remembered in `localStorage` (`wl_home_pos`, 24h, rounded to ~110m).** Module-scope caching alone dies on reload, which meant a fresh `getCurrentPosition()` every load — invisible where the permission is a standing grant, but a **permission dialog on every launch** after a dismissed browser prompt or iOS "Allow Once" (which lapses when the app is backgrounded). Rounded because everything downstream wants a neighbourhood, not a doorstep.
- **Picking people = `components/match/PeoplePicker.tsx`** — the one picker (search → **Clear** → cleared shows only who you've picked, with the pick/drop animations). Used by the collab composer, the organizer lineup, and the new-event composer. **Don't re-implement a picker or drop `MatchFinder` into a fixed-height scrollbox** — a scroll-inside-a-scroll is the worst thing you can do to this app on a phone.
- **Creating a collaboration = `components/vendor/CollabComposer.tsx`** — the one composer (name + description + `PeoplePicker`). The dashboard Create card, `/vendor/collab/new`, and the Add-people modal all render it, so they can't drift. It returns `occasionId`; deep-link into the new chat with `/vendor/messages?tab=collabs&collab=<id>` (events: `/vendor/organize?event=<id>`).
- **Lineup roles are inferred, not asked** (`lib/lineup-roles.ts` `inferRole()`), from what the business already is. No "invite as" step.
- **A collaboration has TWO states = `lib/collab-status.ts`** — `Planning ──▶ Active` (+ the event it becomes). Active = you and ≥1 other business are in (`agreedCount >= 2`, or an event exists) — the same threshold that unlocks Create-event, so the chip and the button always agree. Green Active / grey Planning, colour on the **chip only** (a card washed amber reads as an error). `collabStatus()`/`collabRoster()`/`collabWhenLabel()`/`collabWhere()`/`compareCollabs()` are shared by the dashboard rail and the Messages tab so they can't drift. **A collaboration is never "blocked" by people who haven't replied** — it goes ahead with whoever's in, and pending invitees are a detail on the roster line, never the headline. Don't add states describing our plumbing ("Confirm you're in", "Event scheduled"): the roster flag lives in the room where its button is, the event lives on the Event link. Sort = `compareCollabs` (soonest first, then Active above Planning) on **both** surfaces.
- **Creating the event LOCKS the lineup.** It's snapshotted from who's `agreed` at that moment (`api/vendor/rooms/[id]/event`), so afterwards `PATCH …/members` returns **409** — enforced in the API, not hidden in the UI — and "I'm in" becomes **"Request to join"**, which reuses the existing self-join (`POST /api/events/join`, `from_id === to_id`) landing in the host's Organize → Lineup tab. No new table, no second approval UI. `getRoomRoster()` returns each member's `lineup` state once the event exists.
- **Google Places = money. `lib/places.ts` owns the spending rules** (read the header before touching it). Google bills **per request, not per result**, so capping results saves nothing — the savings are: (1) **search on submit, never on keystroke** (this used to fire a Text Search per keypress: ~13 billed calls per onboarding, now **2**); (2) **24h caches** for search + details (inside Google's 30-day cache terms; the CapRover container is long-lived so they survive); (3) **never re-buy** — Text Search already returns geometry/rating/types/price/status, so `PlaceCandidate` keeps all of it and `placeDetails` asks only for what Text Search can't give (phone, website, editorial summary, address components, hours) and merges. Pass **`region`** (from `navigator.language`) or Google biases on the requesting IP — which is *our server*, so every user worldwide gets datacenter-ranked results.
- **Master-detail everywhere**: a list of cards → open one → it becomes the title with a specific back link (`‹ Events`, `‹ Collaborations`). Add `VendorBackBar` exclusions for pages that own their own back, and prefer a separate view over stacking another block on a long scroll.
- Map uses react-leaflet (Leaflet v1)
- Styling via Tailwind v4
- **Clerk API in this version:** `SignedIn`/`SignedOut` don't exist — use `<Show when="signed-in">` / `<Show when="signed-out">`. `UserButton` has no `afterSignOutUrl` prop. Auth components must be `'use client'`. Server-side: `import { auth } from '@clerk/nextjs/server'`.
- **Member profile pages are server components** — only `ShopSection` and `ActionBar` are client-side.
- **Unclaimed profiles** (`member.status === 'unclaimed'`) show a claim banner. Claim flow at `/claim/[memberId]` verifies via connector-agent then calls `/claim-profile` to flip status.
- **Composio action names** (verify against docs before coding): `SHOPIFY_LIST_ALL_PRODUCTS`, `SQUARE_LIST_CATALOG`, `SHOPIFY_CREATE_ORDER`.
