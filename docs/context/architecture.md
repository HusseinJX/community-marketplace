## Architecture
- **App shell = Instagram-style nav** (`app/layout.tsx` + `ClerkProvider`/`StoreProvider`): `components/TopNav.tsx` (left `+`→`/share`, center **WhatsLocal ▾** dropdown = Home/Feed/Events, right cart) + `components/BottomNav.tsx` (Home / Reels→`/live` / Messages→`/messages` / Search→`/explore` / Profile→`/shopper`). Replaced the old `components/auth-nav.tsx` (now unused). Safe-area aware (`viewport-fit=cover`, notch padding, scale locked to stop iOS input-zoom).
- `app/page.tsx` — member browse/map page (main landing); hero has **Shopper admin** (`/shopper`) + **Admin demo** (`/vendor`) buttons
- `app/explore/` — IG Explore-style full-bleed square-tile grid of local members + name search (client; `listMembers` + demo fallback)
- `app/share/` + `components/share/ShareComposer.tsx` — Twitter/IG-style post composer: text, image/video upload (`/api/share/upload`), tag a business or event (search **or QR scan** — auto-detects `/members` vs `/events`·`/live`), livestream link → `POST /api/posts`
- `app/shopper/` — shopper "admin"/account dashboard (Saved/Cart/Orders); sign-in/account control (Clerk). Community section links to **Explore local resources** (`/resources`) and **Petitions & causes** (`/petitions`)
- `app/messages/` — Messages tab: a pinned **WhatsLocal Assistant** conversation card → `/messages/assistant` (`components/messages/AssistantChat.tsx`), plus a "DMs coming soon" stub. The assistant is the **one brain** — `app/api/assistant/chat` proxies the connector's streaming `chat-stream` (per-device `sessionId`), with a local-concierge fallback (live `marketplace-search`) when the connector is down. See "One brain" in Recent Decisions.

Reached from the dashboard **Tools** grid (not the slim top nav)
- `app/vendor/messages/` — vendor **inbox** (a nav tab): (1) **customer DMs** — real conversations customers had with the business agent (reads `chat_conversations`/`chat_messages` via `app/api/vendor/messages` + `.../[conversationId]`, `resolveActor`-gated), each opening the transcript inline; (2) a pinned **"Your AI agent"** card → `app/vendor/messages/assistant/` where the owner chats with their own business agent (`components/vendor/VendorAgentChat.tsx` streaming `/api/chat/[memberId]`).
- **Inbound phone agent** (`lib/business-phone.ts` + `app/api/voice/context` + `app/api/voice/lead`) — a real phone number answered by the business's own AI agent, same brain as the profile widget (`buildBusinessContext`, so they can't drift). **The connector's old voice line routes on WHO IS CALLING (caller ID → onboarding); a business line routes on WHICH NUMBER WAS DIALLED.** ONE Telnyx assistant (`assistant-24da91ae-…`) serves every business; both webhooks are authed by `VOICE_TOOL_SECRET`. Phone messages write `chat_conversations`/`chat_messages`/`chat_leads`, i.e. the SAME vendor Messages inbox as web chats. **Recording is deliberately OFF** (California two-party consent — the greeting discloses "I'm their AI assistant" but does not ask to record); transcripts come from `GET /v2/ai/conversations/{id}/messages`.
  - **A forwarded call is identified by the SIP Diversion header, NOT by the dialled number** — on a forward, `to`/`telnyx_agent_target` is always OUR number, so routing on it answers every forwarded call as whichever business owns the shared number. `resolveBusinessForCall()` reads `telnyx_sip_header_diversion` first. **This is what lets ONE shared number serve every business** (a business points their existing number at us instead of voicemail) — provisioning is a routing-table row, not a number each. Multi-hop stacks most-recent-first, so the number the caller dialled is the **last** entry.
  - **An unrecognised forwarder resolves to NULL on purpose.** Falling back to the dialled number would confidently answer as the shared number's business to someone who rang a different one; the generic message-taker is the only honest answer to a call we can't attribute.
  - **The header exists ONLY on `assistant.initialization` and is never persisted** on the conversation record — read it there or lose it. `/api/voice/context` therefore mints a **`business_number`** dynamic variable; the Telnyx `capture_lead` tool passes it back and `/api/voice/lead` resolves from it FIRST, because `dialed_number` on a forwarded call is ours and would file the message under the wrong business.
  - **Forwarding setup is a race against the carrier's voicemail** — `**61*…*11*20#` never fires because voicemail answers first (~16s on Boost), while the phone still reports *Enabled*. Use a low timer; the value set is a **floor** (5s → forwards at 10–11s). Vendor-facing codes per carrier: **`docs/phone-forwarding-by-carrier.md`**. ⚠️ Verified on **Boost only** — some carriers strip Diversion or use `History-Info`, which `extractDiversion` does NOT parse.
  - **What the phone agent can do, and what's deliberately NOT built yet (2026-08-11).** It **answers questions about products, prices and descriptions with NO tool call** — `buildBusinessContext` emits a `## Products for sale` block (name, price, description) plus events, hours and owner FAQs straight into the prompt, which is also faster than a tool round-trip on a live call. Actions are webhook tools on the Telnyx assistant (each = an authed `/api/voice/*` endpoint + a tool definition): **`capture_lead`** (take a message), **`request_booking`** (`/api/voice/booking`) and **`check_availability`** (`/api/voice/availability`).
    - **Bookings mirror the web flow exactly, so the two can't drift.** Square vendor → real open slots offered and the slot is TAKEN (`confirmed`); everyone else → free-text request the business confirms. **A picked slot IS the date** — derived from the instant city-local, never from the model's separate `requested_date`, or the row and the Square calendar disagree about which day someone turns up (server derives, caller never decides). **Every Square failure degrades to a plain request**, never an error: a calendar outage must not take the booking conversation down. Times are spoken city-local (UTC would offer 9pm for a 2pm slot) and capped at 3.
    - **`today_date` is a dynamic variable for a reason** — a spoken "Thursday" is not a date, and the agent can only resolve it against today. City-local, never UTC. A non-ISO or past date is REJECTED rather than guessed.
    - **The agent must say "request", not "booked"**, unless Square actually reserved it — "you're booked" on an unconfirmed request sends someone to a closed door.
    - **Email is preferred but NOT required** on a call (spelling an address aloud is painful); phone-only is accepted and the agent then says the business will *call back*. Some channel is mandatory — a booking only one party knows about is worse than none.
    - **NEXT, in order: (1) add-to-cart / send the cart link. (2) buying on the call. (3) Calendly** (via Composio or its API) for non-Square vendors — it has real availability rules. **Raw Google Calendar is NOT enough on its own**: free/busy says when someone is BUSY, not when they're bookable; you'd still need hours, service duration, buffers, staff and lead time, which is a scheduling subsystem, not an integration.
    - **`scripts/voice-booking-smoke.mts`** — 21 checks against the real DB (auth, routing, refusals, both contact paths, slot-vs-claimed-date, non-Square degradation), with cleanup. ⚠️ **Square's live API is still UNVERIFIED** — the `real_calendar: true` branch is exercised in shape only.
    - **⚠️ SMS IS NOT AVAILABLE — the carrier registration (10DLC / toll-free verification) has not been passed.** So any "text the caller a link" design is blocked; **email (Resend) is the only outbound channel**. Don't design a phone action around SMS until that clears.
    - **The agent must NEVER take a card over the phone** — PCI scope, and the Telnyx assistant is not a payment terminal. When buying-on-a-call is built, it sends a **link** (email today, SMS once registered) and payment happens in the browser. The instructions still say it cannot take payment; keep that true.
  - `lib/business-phone.ts` is still a hardcoded map (+ `BUSINESS_PHONE_MAP` env override) with one entry. It becomes a `vendor_phone_numbers` table when numbers get provisioned per vendor — **only that file changes**, everything routes through `memberIdForNumber`.
